# 量化面试官到底在看什么——以及如何把它接入 Nox/Nocturnal

这份文档是"资深量化"视角背后的技术清单。每一项都包含:他们会检查什么、为什么检查、以及你可以在这个代码库中做出的具体集成。

## 1. 样本外、考虑成本的表现
**他们会检查:** Sharpe(夏普比率)/Sortino(索提诺比率)、最大回撤(max drawdown)、换手率(turnover),以及——最关键的——回测是否只使用了决策时点已知的信息(即没有前视偏差 / look-ahead bias)。他们会问:"你的样本外 Sharpe 在扣除真实滑点(slippage)之后是多少?"
**集成方式:** 新增一个 `backtest/report_tearsheet.py`(或对应的 C++ 实现),让完整的信号流水线(WS1-6)在历史数据上跑一遍,设定一个硬性截止日期,套用一个基于你现有 `LiquidityGate` 价差数据推导出的滑点模型(使用真实历史价差,而不是零成本成交假设),最终输出 Sharpe/Sortino/MDD(最大回撤)/换手率/容量(capacity)。这是你目前缺失的、价值最高的单一交付物。

## 2. 信号衰减 / 半衰期的合理性
**他们会检查:** 信号衰减是假设出来的,还是估计出来的?你已经有 `HalfLifeDecay` 了——他们会问"你是怎么为每个类别选定半衰期参数的?"
**集成方式:** 按 `SignalCategory` 记录滚动窗口内信号与收益的真实相关性,拟合出经验半衔期,而不是(或者辅助于)手动设定的值。哪怕只是做一个"|相关性| 对信号发出后经过时间"的简单回归,也能给你一个站得住脚的数字,而不是"我拍脑袋定的 24 小时"。

## 3. 集成/融合方法论
**他们会检查:** 基于规则的融合(你的 CONFIRM/CONTRADICT/IGNORE 判定)容易招来"为什么不用学习出来的权重?"这种问题。他们其实是在考察你是否理解其中的权衡取舍,而不是要求你重建整个系统。
**集成方式:** 你不需要用模型取代规则——只需加一层轻量的评估机制:把每一次判定与其后 N 天的前瞻收益(forward return)一起记录下来,并定期计算每种判定类型的命中率(hit-rate)。这能把"我用了启发式规则"这句话,升级成"我用了启发式规则,而且有数据表明 CONTRADICT_bullish_bearish_skew 在 N 个样本中以 63% 的命中率预测出负的前瞻收益"——后一句话才是能让你被录用的关键。

## 4. 数据流水线中的前视偏差与幸存者偏差
**他们会检查:** 内部人集群过滤器(insider cluster filter)、Form 4 抓取、新闻情绪分析——这些都容易在不知不觉中用"事后更正/延迟到达"的数据,当作实时已知的信息来用。SEC 文件披露存在延迟(disclosure lag);要确保你的回测用的是文件的*披露时间戳*,而不是事件本身发生的日期。
**集成方式:** 审计 `fetch_form4_filings()` 和新闻抓取逻辑,确认每一次回测的数据关联(join)都使用了数据的真实可获得时间戳,而不是经济事件发生的日期。把这一点明确写进文档——这是一个常见的面试问题,也是一个常见的漏洞。

## 5. 执行的真实性(execution realism)
**他们会检查:** 你是否对部分成交(partial fills)、排队位置(queue position)、逆向选择(adverse selection)建模,还是假设在中间价(mid)瞬间全部成交?
**集成方式:** 你的 `LiquidityGate` 已经在追踪相对价差的 z-score——把回测扩展为按买卖价(bid/ask,而不是 mid)成交,并根据同一个 z-score 机制来缩放成交价格(价差机制越差,假设的成交价也越差),而不是用一个固定的成本假设。

## 6. 资金容量 / 市场机制的稳健性(regime robustness)
**他们会检查:** 策略在 10 倍资金规模下还能不能跑?是否只依赖某一种市场机制(比如只在高波动率环境下才有效)?
**集成方式:** 既然你已经有 `detect_volatility_catalyst`(VIX 跳变检测)和机制重置(regime-reset)机制,就把你的 tearsheet 按机制分段(重置前/重置后),并报告以机制为条件的 Sharpe——这展示了你理解机制依赖性,而不是只报一个笼统的混合数字。

## 7. 风险控制作为一等公民
**他们会检查:** 名义仓位上限(notional ceilings)、熔断开关(kill switches)、在坏数据下是"失败即开放"(fail-open)还是"失败即关闭"(fail-closed)。这一点你已经具备了——流动性阀门(liquidity gate)的 fail-open 行为其实是一个很好的讨论点(为什么在这里选择 fail-open,权衡是什么)。
**集成方式:** 不需要再造轮子——只需准备好清楚地解释 fail-open 这个选择(一个卡死的阀门若阻断全部交易,本身就是一种风险;你是在权衡"偶尔在坏的流动性数据下继续交易"与"一次数据小故障就系统性地阻断所有交易"之间做取舍)。把这套推理写进 `docs/risk_controls.md`,不要只让它停留在你脑子里的部落知识(tribal knowledge)。

## 8. 可复现性 / 工程卫生(engineering hygiene)
**他们会检查(尤其是量化开发/基础设施岗位):** 测试、CI、日志记录、事故响应流程。你已经有 `tests/test_regime.cpp`、在一次真实事故后新增的持久化日志,以及一套有文档记录的权益对账(equity reconciliation)流程。这已经是你的一个强项——确保它是"可见的"(比如有一份干净的 `docs/architecture.md` 汇总 WS1-6 加执行加对账的完整流程),而不是只存在于你对开发历史的记忆里。

## 如果面试前你只能做几件事,优先级排序
1. 带真实成本的 tearsheet(#1)——不可谈判的一项,没有它其他一切都是次要的。
2. 判定命中率日志(#3)——成本很低,能把启发式规则变成实证证据。
3. 前视偏差审计(#4)——检查它几乎不花你任何成本,但如果你搞错了又不自知,会让你直接丢掉这次面试。
4. 按机制分段的报告(#6)——能让 #1 更加可信。
