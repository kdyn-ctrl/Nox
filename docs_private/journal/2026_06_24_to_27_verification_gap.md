# Private Journal: June 24-27, 2026 — "Already Done" Isn't the Same as Working

*Private mirror of [docs/journal/2026_06_24_to_27_verification_gap.md](../../docs/journal/2026_06_24_to_27_verification_gap.md) with real specifics kept out of the public version.*

## Concrete detail

- `fetchIVRank` computed rank from a single snapshot's min/max instead of real 52-week history — always returned ~50% regardless of actual conditions. Replaced with a variance-risk-premium signal on June 24; then on June 26 discovered the *real* 52-week IV rank logic actually lived in the Python heartbeat service (`calculate_iv_rank`) and was never wired into the C++ signal path that needed it — meaning the June 24 fix was still silently running on the old broken skew-based logic underneath. (As of the last status memory update, this wiring still isn't done — see `project_nox_status.md`'s "Open / Known Issues.")
- `add_position()` was never called anywhere outside documentation — every auto-executed options position was structurally invisible to its own exit logic (profit target, stop-loss, DTE limit). This is the same root defect that resurfaced and got actually fixed in the July 2 trade-ledger session — worth being precise in an interview that this was *found* on June 26 but not *fixed* until roughly a week later, because fixing the write path required also fixing the read path (empty `trade_history`) at the same time.
- The engine didn't compile for a period — two profile struct members used but never declared — meaning the binary I'd been running was several days stale relative to source. Also found: a broken parallel MCPT test silently dropping most of its 1000 permutations with an order-independent statistic that always produced p=1.0 (statistically vacuous, not just buggy); a heartbeat IV fetcher hitting the wrong Alpaca host and 404ing forever; a SEC-filing dedup bug causing infinite re-scans; a qty field silently coercing string→0.0.
- Two Alpaca PATs were pasted directly into chat this week (June 24 and June 26) — flagged and rotated both times. This is the *third* time in the project's history a credential ended up somewhere it shouldn't (see also the June 30 in-chat paste and the July 2 leaked-onto-public-main incident) — a real pattern worth naming honestly rather than treating each occurrence as isolated.
- **The `git filter-repo` data loss**: a private roadmap doc (with a candid weaknesses/interview-prep section) leaked to the public repo; running a full history scrub to remove it rewrote history on *all* local branches, including wiping the same file from the private branch. A recovery attempt via force-push made it worse — restored the file as a 0-byte placeholder, content permanently gone. Resolved pragmatically: deleted the empty file, wrote `DESIGN_THINKING.md` fresh as the public-safe replacement, accepted the loss.

## Interview angle

For [[02_quant_evaluation_criteria]] item #8 (reproducibility/engineering hygiene) — this week is the honest counter-evidence to "I have tests and CI," and I should be ready to say so directly: tests existed and were still wrong (stale expectations edited to match behavior rather than the reverse, in the June 22-23 window), and a binary shipped for days without actually reflecting source. The lesson I'd state out loud: audits need to check "does this actually run," not "does this look done," and I built that habit *because* of this week, not before it.

The `git filter-repo` incident is my best answer if asked "tell me about a mistake with real consequences" — unlike most of this project's bugs, this one caused permanent, unrecoverable data loss, and the honest lesson is that a destructive fix for one problem can create an unrelated, worse problem if I don't think through its full blast radius before running it. I do now, and I can point to later incidents (the July 2 leak) where I explicitly stopped myself before a destructive action for exactly this reason.
