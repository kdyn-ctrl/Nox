# Private Journal: July 1-3, 2026 — Reliability, a Real Leak, and Undoing My Own Over-Engineering

*Private mirror of [docs/journal/2026_07_01_to_03_reliability_and_reversal.md](../../docs/journal/2026_07_01_to_03_reliability_and_reversal.md) with real specifics kept out of the public version.*

## Concrete detail

- `PositionManager::add_position()` was never called after `OptionsSignalGenerator` routed a live order — every options trade placed automatically was invisible to the exit monitor. `trade_history` was empty for the same structural reason, so every performance report that week was reporting "no trades" regardless of reality. Fixed and tested against a throwaway DB copy first. In the same pass, caught that a newer rule-based equity exit path bypassed the T+1 settlement gate for CN A-shares — a real regulatory-violation risk (illegal same-day round-trip), not just a bad trade, caught before it ran live.
- Also found and fixed: a stray advisory Telegram call left in the options scanner (spam, not a bug); a stray `/v2` suffix in `ALPACA_BASE_URL`; `strike_price` parsed as numeric when Alpaca actually returns it as a string (crashed spread orders); `qty`/`ratio_qty` serialized via `std::to_string()` into JSON strings (rejected by Alpaca) — same pattern as the June 29 spread-order bug, in a different call site, meaning the earlier "fix everywhere with this pattern" pass had missed one; the T+1 CN-only settlement gate was logging every US equity buy into `china_positions.json`, not just CN A-shares.
- **Alpaca trailing-stop closures went unrecorded** — the broker executes trailing stops automatically, but nothing in Nox was listening for that event, so positions closed on Alpaca's side vanished from Nox's internal state with no SELL ever recorded. Fixed with a 5-minute polling monitor that detects the closure and synthesizes the missing SELL + Telegram alert. This is a "missing feature," not a bug, and worth framing that way — the system had literally no path to observe broker-side actions it didn't itself initiate.
- **The real July 2 leak:** the private→public port actually pulled the IBKR client (whose own migration doc says explicitly never merge to public), the full China data engine, real trading-edge modules, and a personal email onto `upstream/main`. First instinct was to delete the leaked files outright; stopped before doing that because the code was load-bearing (deleting it would break a live running pipeline, not just remove a nice-to-have). Re-scoped to a denylist + an automated secret-scanner (gitleaks) + a pre-push hook, then force-pushed cleaned history. This is the leak-response I'd point to as the mature one, in direct contrast to the June 30 in-chat paste and the June 24-27 `git filter-repo` incident — same category of mistake, progressively better-handled each time.
- **Repo-split reversal:** the private/public two-branch structure (`main` + `nocturnal` on one repo) had become actively counterproductive — files ending up on the wrong branch, a rebase between `upstream/main` and `private/main` that diverged badly enough to abort. Said so directly and consolidated to one working tree, two remotes, and a pre-push safety hook instead of a branch split. I'm treating this as a genuine reversal of my own earlier decision, not a failure — the original split was a reasonable response to the leak history above; it just didn't hold up once the actual workflow cost became clear.
- The `asset_class` schema incident: `no such column: asset_class` on daily report generation. The migration code (`ALTER TABLE ADD COLUMN` guards in `heartbeat/monitor.py`) existed and should have self-healed, but hadn't actually run against this container's live database — schema-in-code and schema-on-disk had drifted. Fixed manually with `ALTER TABLE` statements, verified, and left a note to check whether migrations actually execute rather than assuming they did.
- A real live test week (this is the part covered in more depth in `reports/paper_journal.md`): AAPL bought roughly a dozen times in a 30-minute-cycle loop because rule-based exits never got a chance to fire before Alpaca's own trailing stop closed the position first; META sat unmanaged for multiple days; every exit that fired that week was a loss. Trade history was archived before a full paper-account state reset heading into the next test week.
- A smaller, non-technical mistake: misread "update the career doc for the Tsinghua-Columbia dual master's" as "restructure the whole plan," pushed a wholesale rewrite, was corrected, reverted to the narrow fix, and said so plainly rather than quietly fixing it and hoping it wasn't noticed.

## Interview angle

For [[02_quant_evaluation_criteria]] item #8, the `asset_class` migration incident is a clean, small example of "schema-in-code ≠ schema-on-disk" that's worth having ready as a fast answer rather than always reaching for the June 28 crash.

## Where things stand as of this writing (2026-07-03) — and what's still open

Still unresolved, and worth stating as unresolved rather than glossing over: the `HalfLifeDecay` config is inconsistent (env-var loading exists, but a later change switched the constructor to hardcoded defaults — unclear which wins without checking the current code directly before claiming either in an interview); two HTTP retry implementations (`monitor.py`'s ad-hoc June 29 version and the July 2 `retry_utils.py`) haven't been consolidated; `china_positions.json` is gitignored as sensitive with no documentation of why. Per [[project_nox_status]], the next real priorities are wiring true 52-week IV rank into the C++ signal path (still only reachable from Python as of the last status check), backtesting integration for options strategies, and bringing up the IBKR paper-trading path. Per [[02_quant_evaluation_criteria]], the single highest-leverage thing still missing is a proper out-of-sample tearsheet with realistic costs — everything else on that checklist is secondary until that exists.

The bot is still actively being tweaked, not shipped-and-done — the July week's live test specifically exposed that the exit logic doesn't yet reliably win against a broker-side trailing stop, and that's the immediate thing being worked through rather than a finished feature. I'd rather describe the system honestly as "currently correct, under continuous adversarial testing against real market behavior" than claim a stability it hasn't earned yet.
