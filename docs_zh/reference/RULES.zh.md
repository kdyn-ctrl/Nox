# Nox 交易系统 — 架构规则与设计契约
# 版本 1.0 | 作者：Van Hellsing
# 适用范围：涵盖当前所有容器（analyst、execution、heartbeat）以及未来的所有模块。
# 本文档是系统行为、边界与扩展标准的唯一权威来源。

 第一节 — 核心系统架构（机器人必须做的事）
════════════════════════════════════════════════════════════

[RULE-001] 分析师心跳循环
  analyst-brain 容器必须以不低于每 24 小时一次的频率执行行情状态（regime）评估周期。
  该周期间隔必须由运行时注入的 ANALYST_CYCLE_HOURS 环境变量控制。若启动时该变量缺失，
  容器必须记录 [FATAL] 错误并立即退出——绝不能静默回退到任何硬编码默认值（参见 RULE-009）。
  硬编码的 sleep_for(hours(24)) 不是有效实现；该间隔必须从环境变量读取，以便在波动性升高的
  行情阶段（例如收紧到 1–4 小时）无需重新构建代码或重启容器即可调整。

  在每个周期中，分析师必须获取两个主要宏观输入：SPY 收盘价相对其 200 日简单移动平均线
  （数据来源为 Alpaca Data API）的位置，以及当前 VIX 水平（数据来源为 Yahoo Finance）。
  这两个输入直接馈入 RegimeStateMachine。若任一数据源获取失败，该周期必须被标记为无效——
  该状态机绝不能基于过期或不完整的数据进行评估。未来的数据源（期权流、收益率曲线、
  板块轮动）可以作为补充输入被加入，但不得取代 SPY/SMA 与 VIX 作为主要的行情状态触发条件。

[RULE-002] 行情状态分类
  位于 shared/RegimeStateMachine.hpp 的 RegimeStateMachine 是对宏观市场状况进行分类的唯一
  权威来源。它必须始终将市场准确归类为以下三种运行状态之一，其参数由前向优化（walk-forward
  optimization）推导得出：

    • RISK_ON     — 有利的市场条件（例如 SPY 位于其 200 日 SMA 上方，且 VIX 低于恐慌阈值）。
                    全额资金部署（乘数 = 1.0）。

    • TRANSITION  — 不确定的市场条件（例如 SPY 正向其 200 日 SMA 回调，但尚未确认进入下行趋势）。
                    降低资金部署（乘数 = 0.5）。

    • RISK_OFF    — 恐慌或高波动条件（例如 VIX 突破优化后的阈值 35，或 SPY 跌破其 200 日 SMA
                    超过 2%）。所有新建仓均被暂停（乘数 = 0.0）。

  具体的 VIX 阈值与 SMA 缓冲百分比定义并记录于 RegimeStateMachine.hpp 中，且可能根据回测
  结果发生变化；本规则记录的是预期行为，而非具体的硬编码数值。该状态机在启动时默认为
  TRANSITION，直到实时数据解析出一个有效状态为止。

[RULE-003] 载荷序列化与内部路由
  每次评估完成后，分析师必须将完整的行情状态结果序列化为经过校验的 JSON 载荷，并通过
  HTTP POST 经由共享的 nox_net Docker 桥接网络发送至执行引擎地址：
  http://execution_engine:8080/webhook。
  载荷必须包含以下字段：secret_key、ticker、action、price、risk_tier、vol、regime_state、
  atr、kelly_pct、report_body。任何字段都不得省略。未来为新增资产类别添加的载荷字段
  （期权 Greeks、期货基差等）必须作为可选的扩展字段加入，且不得破坏向后兼容性。

[RULE-004] 执行引擎服务器
  execution-engine 容器必须在 0.0.0.0:8080 上维护一个持久的多线程 HTTP 监听器。每一个
  收到的请求在任何逻辑执行之前都必须依次通过三道关卡：
    1. 模式关卡（Schema Gate）— 使用 nlohmann/json 严格解析载荷。任何格式错误的输入
                         都会在发生内存分配之前被拒绝，并返回 HTTP 400。
    2. 鉴权关卡（Auth Gate）— secret_key 字段必须与 WEBHOOK_SECRET_TOKEN 环境变量匹配。
                         任何不匹配都会被静默丢弃并记录为 WARN 级别日志。
    3. 逻辑关卡（Logic Gate）— RSI 动量过滤器：RSI 高于 70 的 BUY 订单将被拦截（超买）；
                         RSI 低于 30 的 SELL 订单将被拦截（超卖）。
  只有通过全部三道关卡的载荷才能进入凯利仓位计算与订单路由环节。

[RULE-005] 通过凯利计算器进行仓位管理
  所有仓位规模都必须由凯利计算器（Kelly Calculator）按以下公式计算：
    K% = W - ((1 - W) / R)
  其中 W 为胜率，R 为盈亏比，二者均在运行时通过环境变量（KELLY_WIN_RATE、
  KELLY_WIN_LOSS_RATIO）注入。原始的凯利输出结果随后会被一个动态安全乘数
  KELLY_FRACTION 缩放，该乘数同样通过环境变量注入，以便根据回测结果快速调优，
  而无需修改代码。系统强制执行以下硬性上限：
    • 单笔交易最大风险：账户权益的 10%
    • 单笔交易最小风险：账户权益的 1%（若策略处于激活状态）

  每次下单前都会从 Alpaca 实时获取账户权益。若获取失败，引擎绝不能使用任何回退值
  或估算的权益值继续执行。而必须：
    1. 以指数退避的方式最多重试 3 次获取权益：2 秒 → 4 秒 → 8 秒（与 RULE-007 一致）。
    2. 若全部重试均失败，立即暂停本周期的所有新订单进入。
    3. 将该失败记录为 [CRITICAL] 级别，输出到容器标准输出。
    4. 通过心跳监控器的通知渠道触发一条 Telegram 告警（参见 RULE-006）。
  静默降级回退是不被允许的——它会掩盖一次真实的基础设施故障，并直接违反
  RULE-013 中规定的双通道可观测性强制要求。
  未来的资产类别（期权合约、期货合约）必须实现各自的仓位适配器，但必须调用并遵循
  同一个凯利百分比输出——它们绝不能覆盖或绕过 10% 的硬性上限。

[RULE-006] 心跳监控器（Nox）
  heartbeat-monitor 容器必须持续承担以下三项职责：
    1. SEC 雷达       — 每 30 秒轮询一次 EDGAR，检索匹配当前监控名单的新 8-K 备案文件。
                         一旦匹配，将备案文本经由 Claude AI 风险分析流水线处理，并向
                         Telegram 推送一条结构化告警。
    2. 每日侦察       — 每个交易日美东时间上午 11:30，汇总宏观新闻头条
                         （Alpaca News API）与目标 SEC 备案文件，生成一份 Claude 撰写的
                         每日情报简报，推送至 Telegram 频道。
    3. 对话式代理     — 维护一个持久的 Telegram 机器人接口，允许通过 /status 命令或
                         自由文本对持仓状态、审计历史与系统状态进行实时查询。
  所有审计报告与交易历史都必须持久化到 SQLite 记忆库（memory bank），路径为
  /app/data/memory_bank.db。该记忆库是系统的机构知识库，必须以持久化 Docker 卷的
  形式挂载。

 第二节 — 安全与架构边界（机器人绝不能做的事）
════════════════════════════════════════════════════════════

[RULE-007] 禁止静默的周期失败（禁止数据丢弃）
  若分析师由于任何原因（容器不可达、网络超时、非 200 响应）未能将其载荷送达执行引擎，
  它绝不能静默跳过该周期并休眠 24 小时。它必须立即进入指数退避重试循环：最多尝试
  5 次，延迟分别为 2 秒 → 4 秒 → 8 秒 → 16 秒 → 32 秒。若所有尝试均耗尽，该失败必须
  以 CRITICAL 级别记录，并标记为需人工复核。本规则适用于所有未来的容器间通信，
  不仅限于分析师到执行引擎这一路径。

[RULE-008] 禁止无防护的外部网络调用
  每一次对外部 API（Alpaca、Telegram、Yahoo Finance、SEC EDGAR、Anthropic，或任何未来
  接入的服务）发起的同步 HTTP 调用，都必须在客户端构造时明确设置连接与读取超时阈值。
  强制执行的最低阈值为：
    • 连接超时：5 秒
    • 读取/响应超时：10–15 秒
  任何网络调用都不得无限期阻塞。本规则适用于技术栈中的所有语言（C++ httplib、
  Python requests）。超时设置不是可选配置——它们是不可协商的安全护栏。

[RULE-009] 禁止硬编码密钥或凭证
  任何 API 密钥、webhook 令牌、机器人令牌、secret key，或任何敏感凭证，都绝不能以
  原始字符串字面量的形式出现在任何容器的任何源代码文件中。所有此类值都必须在运行时
  通过环境变量注入，来源于一个明确列入 .gitignore、且从不提交到版本控制中的 .env 文件。
  若启动时缺少必需的环境变量，容器必须记录 [FATAL] 错误并立即退出，而不是尝试以
  降级状态运行。本规则适用于本系统未来添加的所有模块、脚本与集成。

[RULE-010] 禁止手动解析载荷
  本系统中的任何组件都不得使用手动字符串扫描、字符偏移索引、子串切分或自定义
  分词逻辑来解析传入的 JSON 载荷。所有载荷的反序列化都必须使用该容器所对应的
  指定原生校验库：
    • C++ 容器    → nlohmann/json，配合结构化异常处理
    • Python 容器 → 标准 json 模块或用于模式校验的 pydantic
  格式错误的输入必须在解析器边界处、在任何字段访问或业务逻辑执行之前就被拒绝。
  解析器异常必须在处理器层面被捕获，并返回 HTTP 400。

 第三节 — 扩展标准（未来功能的规则）

[RULE-011] 期权与期货模块集成
  当添加期权或期货交易模块时，必须遵循以下要求：
    • 行情状态关卡：在任何订单被计算规模或路由之前，必须先读取当前的行情状态。
      RISK_OFF 状态必须暂停所有新建仓，包括卖权（short-premium）策略。
    • 凯利适配器：必须实现资产类别专属的仓位适配器（例如期货的合约乘数归一化，
      或期权的 delta 调整名义价值），其输出为一个凯利百分比，该百分比随后同样
      受 RULE-005 中定义的 10% 硬性上限约束。
    • 载荷契约：新的信号字段（例如 strike、expiry、delta、theta、IV_rank）必须
      作为可选的、命名清晰的扩展字段加入现有载荷模式中。它们不得重命名或挪用
      现有的必需字段。

[RULE-012] 新容器与服务标准
  任何添加到 docker-compose.yml 中的新服务都必须：
    • 归属于 nox_net 内部网络，以实现服务间通信。
    • 定义 restart: unless-stopped 策略。
    • 仅通过引用 .env 的 environment 代码块注入所有凭证。
    • 在 docker-compose.yml 中包含明确说明其职责范围的注释。
    • 若该服务暴露任何 HTTP 端点（无论内部还是外部），必须遵循同样的三道关卡校验
      模型（模式、鉴权、逻辑）。

[RULE-013] 可观测性与可审计性
  每一笔执行的订单、每一次行情状态转换、每一条 SEC 雷达告警，都必须同时产生一条
  结构化日志记录（容器标准输出）以及一条 Telegram 通知。静默执行——即系统在没有
  对应的、用户可见记录的情况下采取行动——是不被允许的。未来的功能必须维持这一
  双通道可观测性标准。结构化日志格式为：[LEVEL] [COMPONENT] Message。
  可接受的级别为：INFO、WARN、ERROR、FATAL、CRITICAL。

[RULE-014] 模拟交易优先策略
  所有新的交易策略、资产类别集成以及执行逻辑修改，都必须先在 Alpaca 模拟交易
  （Paper Trading）环境中完成验证，然后才能部署任何实盘资金。API 基础 URL 必须
  通过环境变量管理，以便在不修改源代码的情况下从模拟环境干净地切换到实盘环境。
  不允许存在任何硬编码的实盘交易 URL。

 第四节 — 实盘资金 AI 护栏（严格模式）
════════════════════════════════════════════════════════════

[RULE-015] 禁止由 AI 控制订单规模或执行
  在任何情况下，LLM 或生成式 AI 模型（Anthropic、OpenAI，或任何未来的服务商）都
  不得直接决定交易规模、订单方向、限价或执行路由。AI 层的职责严格限定于：
    • 对 SEC 备案文件与宏观新闻头条进行文本摘要。
    • 情绪排序与定性风险评述。
    • 通过 Telegram 发送审计追踪告警。
  所有量化的执行边界——包括但不限于仓位规模、价格校验、动量过滤器以及止损设置——
  都必须完全由执行引擎内部、编译期确定的确定性 C++ 数学算法来评估。LLM 的输出
  绝不能在未经过一个经过校验的、确定性的解析与边界检查层之前，被直接用作订单
  载荷中的数值输入。

[RULE-016] AI 输出模式校验与回退机制
  任何馈入系统状态的外部生成式模型响应（例如 process_automated_filing() 中的
  Claude 8-K 风险分析），在其取值影响任何下游逻辑之前，都必须先按照一个严格的、
  预定义的模式进行解析。
    • 模型必须被提示以结构化格式作答。当前 SEC 备案文件分析所要求的格式为：
        RISK_FACTOR: [0.1–1.0] | SUMMARY: [一句话摘要]
      未来的集成必须先在本 Rules 文档中定义并记录各自的模式，然后才能编写代码。
    • 解析逻辑必须捕获所有校验失败情形：截断输出、缺失字段、超出范围的数值，
      以及非数字的 RISK_FACTOR 字符串。
    • 若解析器因任何原因未能解码 AI 输出，系统必须回退到最保守的安全状态
      （例如 RISK_FACTOR = 1.0 / 高风险），而不是崩溃、静默记录日志，或使用
      部分解析的字符串。
    • 一次解析失败必须以 [WARN] 级别记录，并上报到 Telegram 频道，以便操作员
      知悉该 AI 响应不可用。

[RULE-017] 外部 API 隔离与限流韧性
  任何与 AI 相关或通知服务的故障，都绝不能阻塞或降级核心交易循环（分析师评估
  周期或执行引擎 webhook）的运行。
    • 所有 AI 操作（heartbeat/monitor.py 中的 Anthropic 调用）都必须运行在
      与执行引擎请求路径完全解耦的、隔离的非阻塞守护线程或微服务中。
    • 每一个与 LLM API 交互的线程或协程都必须强制执行一个专属的 15 秒超时上限——
      与 RULE-008 中定义的交易所 API 超时相互独立——以防止一次挂起的 Anthropic
      调用拖住 Telegram 通知循环或计划任务。
    • 任何 AI 服务商返回的 HTTP 429（限流）响应都必须被显式捕获，以 [WARN] 级别
      记录，并采用线性退避（例如 5 秒 → 10 秒 → 15 秒）后再重试。它们绝不能
      作为未捕获异常向上传播并终止调用线程（另见 RULE-007 以及 Patch C 中
      新增的 schedule_checker 防护）。
    • 执行引擎（C++）绝不能对任何 AI 库存在导入或运行时依赖。该边界在容器层级
      强制执行。

[RULE-018] 动态仓位硬性关卡
  执行引擎必须在构造或发送任何订单载荷之前，对每一个计算出的股数施加一个
  双条件的物理关卡：

    条件一 — 零股拦截：
      若凯利计算器返回的股数为 0（即分配的美元金额小于单股价格），该订单必须
      被中止并以 [CRITICAL] 级别记录。严格禁止引擎将一个零股结果强行提升为
      最低 1 股买入，如果该单股价值超过当前账户权益 10% 的最大风险限额。

    条件二 — 名义价值上限：
      在路由任何订单之前，引擎必须校验：
        （数量 × 当前价格）≤（实时账户权益 × 0.10）
      若该条件因任何原因被违反（例如在计算仓位与提交订单之间发生了价格跳空），
      该订单必须被立即拦截，并向 Telegram 触发一条 [CRITICAL] 告警。

  这两个条件都是不可协商的，且适用于所有资产类别。在生产环境中，没有任何
  覆盖开关、环境变量或运行时参数可以禁用其中任何一个条件。

 第五节 — 中国 A 股市场约束
════════════════════════════════════════════════════════════

[CN-RULE-001] 板块整手截断（手，shǒu）
  所有 A 股订单数量都必须以配置的整手规模（CN_BOARD_LOT_SIZE，默认 100 股）的
  整数倍提交。在凯利计算器或任何固定档位仓位路径产生原始股数之后，执行引擎必须
  向下截断——而非四舍五入——到最接近的较低整数倍，然后才能构造订单载荷。

  截断公式：
    submitted_qty = floor(raw_qty / CN_BOARD_LOT_SIZE) * CN_BOARD_LOT_SIZE

  若该截断产生的 submitted_qty 为 0，引擎必须：
    1. 立即中止该笔交易——绝不能提交零股（不足一手）订单，也不能向上凑整到一手。
    2. 将该事件以 [CRITICAL] 级别记录到容器标准输出。
    3. 触发一条 Telegram 告警，标明该股票代码、原始凯利数量以及配置的整手规模。
    4. 直接返回，不得触碰 Alpaca。

  该行为与 RULE-018 中的零股规则相呼应：不允许进行不足一手的买入，因为它会
  占据凯利分配额中不成比例的过大百分比，违背 10% 名义价值硬性上限的精神。

  CN_BOARD_LOT_SIZE 是一个默认值为 100 的环境变量。如果交易所规则发生修订，
  可以在不修改代码的情况下覆盖该值。它必须是一个正整数；无效或非正数值必须
  回退到 100，并附带 [WARN] 级别日志。

[CN-RULE-002] T+1 交割制度强制执行
  中国 A 股市场依据 T+1 交割规则禁止当日回转交易。在交易日 T 买入的持仓，
  不能在 T+1 之前卖出。执行引擎必须在信号分发层面强制执行该规则，具体如下：

  当 BUY 得到确认（券商返回 HTTP 200）时：
    • 在进程内的 ChinaPositionRecord 映射表中记录该股票代码与建仓日期。
    • 立即将完整的映射表持久化到 CN_POSITIONS_PATH 所指向的文件
      （默认为 /tmp/china_positions.json），以便该状态在引擎重启后依然保留。

  当收到 SELL 信号（在发起任何券商调用之前）时：
    • 确定有效的卖出日期：若信号中存在 trade_date 字段则使用该字段；
      否则使用当前系统日期。
    • 在持仓映射表中查找该股票代码。
      - 若找到，且 sell_date == entry_date：丢弃该信号——记录 [CRITICAL] 级别日志，
        触发一条 Telegram 告警，并直接返回，不向券商路由任何订单。
      - 若找到，且 sell_date > entry_date：允许该信号正常继续执行。
      - 若未找到：记录 [WARN] 级别日志（该持仓可能早于本引擎实例存在），
        并允许该卖出继续执行——无限期阻塞的后果会比一次未经验证的卖出更糟。

  当 SELL 得到确认（券商返回 HTTP 200）时：
    • 将该股票代码从映射表中移除，并重新持久化该文件。

  引擎启动时：
    • 加载已持久化的 JSON 文件。丢弃所有 entry_date 严格早于今天的记录
      （它们至少已经满足 T+1，限制已经解除）。以 [INFO] 级别记录已加载与
      已丢弃的记录数量。

  回测模式：信号载荷可以包含一个 trade_date 字段（格式为 "YYYY-MM-DD"），
  用以注入模拟时钟。所有回测生成的 BUY 与 SELL 信号都必须包含该字段；
  在模拟环境中依赖系统时钟会产生错误的关卡行为。

  在生产环境中，没有任何覆盖开关、环境变量或 API 参数可以绕过 T+1 关卡。
  若在特殊情况下需要平掉一笔当日持仓，操作员必须直接通过券商仪表盘进行
  操作——交易所本身会在撮合引擎层面强制执行 T+1 规则。

  CN_POSITIONS_PATH 是一个控制持久化文件路径的环境变量。它默认为
  /tmp/china_positions.json。对于生产部署，请挂载一个持久化卷，并将该变量
  指向该卷内的一个路径，以确保状态能在容器重启后依然保留。
